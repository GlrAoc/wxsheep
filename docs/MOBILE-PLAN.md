# MOBILE PLAN · 向手机端进发

> 结论先行：**不要一上来就做视觉识别**。先用一个几乎零成本的实验判断
> "PC 和手机的牌面是不是同一张"，这个结论直接决定后面走哪条路。

---

## 1. 现状与能力边界

PC 路线之所以能闭环，靠的是一条**专属通道**：RadiumWMPF 在读取
"远程调试配置"结构时被 frida 打桩，从而把小程序页面的 CDP 打开。这条通道
在 Android 上**不存在**——手机微信的小程序容器是 XWeb，没有对应结构可 Hook。

已确认的手机侧条件（本次实机探测）：

| 项 | 值 |
|---|---|
| 设备 | RMX3700（真我 GT Neo5 SE），已 root（KernelSU Ultra） |
| 系统 | Android 14 / SDK 34 |
| 分辨率 / 密度 | 1240×2772 / 560，Override 476 |
| adb | 可用，`C:\platform-tools\adb.exe`，设备序列号 `d284ed5f` |
| 抓图 | `adb exec-out screencap -p` 正常，PNG 约 160 KB |
| 点击 | `adb shell input tap x y`（待校准） |
| 视觉依赖 | opencv / numpy / PIL 全部就绪 |

## 2. 三条路线

| | 读牌方式 | 是否需要 root | 精度 | 工程量 | 结论 |
|---|---|---|---|---|---|
| **A · 视觉 + adb** | 截图 → 牌区定位 → 图标聚类 → 遮挡推断 | 否 | 中（暗牌漏检、图标误判） | 中 | 兜底路线 |
| **B · root + frida 读 XWeb** | 注入 XWeb / JS 引擎，直接读游戏对象 | 是 | 高（等同 PC） | 大，且随微信升级崩 | 只在 A 不行时投入 |
| **C · 关卡指纹复用** | 复用 PC 端已有的 `map_md5 + map_seed` 复现整张牌面 | 否 | 高 | **小** | **先验证** |

### C 为什么值得先试

牌面完全由 `map_md5 + map_seed` 决定（21 字节头 + protobuf GameMap，
花色由 seed 经 XorShift + Fisher-Yates 分配）——这套复现逻辑我们已经在
PC 上验到「18 张 / 243 张两种情况 `identical`，零失配」。

如果**同一账号同一天，PC 和手机的每日关卡是同一张图**，那么手机端根本
不需要视觉求解：

```
PC 读牌 → 求解（已验证的 dfs_nopark）→ 按坐标换算 → adb tap 到手机
                                   ↑
                        视觉只做"每步校验"，不做"结构重建"
```

这比在手机上重建 500 张牌的遮挡图要可靠一个数量级。

## 3. 关键实验（按顺序做，前一个失败才做后一个）

### 实验 1 · 两端是否同牌 —— 成本 10 分钟，结论最硬

> 前置条件：需要一个**当天还没打过**的关卡。2026-11-24 这轮 PC 端已经清完
> （结算页「今天已挑战成功」），所以实验 1 安排在**次日刷新后**，或用另一个账号。
> 实验 1 之前不需要动手机上的任何东西。

1. PC 端进该关，只读不点：
   ```bat
   oneclick.cmd --dry
   ```
   产物：`dbg\sheep-solver\auto_*_stage1.board.json`（含牌数、花色分布、坐标）
2. 手机端进**同一关**，抓图：
   ```bat
   node mobile\adb_probe.js
   python mobile\analyze_shot.py mobile\shots\shot-*.png
   ```
3. 比对三件事：**总牌数**、**花色种类数**、**最外层牌的相对位置**。

| 结果 | 结论 |
|---|---|
| 三项都对得上 | 走 C：手机端只做坐标映射 + 每步视觉校验 |
| 牌数不同 | 每日关卡按设备/账号下发不同 seed → 走 A |
| 牌数同但花色分布不同 | 走 A（同结构不同着色，可能是皮肤差异） |

### 实验 2 · 手机端视觉可读性（只在实验 1 失败时做）

`analyze_shot.py` 的输出就是闸门：

- 暗牌（被压住的牌）检出率 —— 目标 > 80%
- 花色聚类数 —— 应与实际种类数一致（通常 7~10）
- 若「全部被判为亮牌」→ 阈值需要按手机截图重调（PC 与手机的色彩管理不同）

### 实验 3 · 点击精度

`adb shell input tap x y` 用的是**物理分辨率坐标系**（1240×2772），与
`screencap` 输出一致，理论上不需要缩放。仍要验：

1. 抓图 → 算出某张牌中心
2. tap → 等 400ms → 再抓图
3. 该牌消失 / 进入槽位 = 坐标正确

注意：手机动画比 PC 慢，点击间隔要用 `--tick 250` 起，并按"点后截图确认"闭环，
不能像 PC 那样按固定步长连点。

## 4. 执行侧的抽象（无论走哪条读牌路线都一样）

```
mobile/
├─ adb_probe.js      设备信息 + 抓图（已完成，可直接用）
├─ analyze_shot.py   视觉可行性判断（已完成，PC 上验证过跑通）
├─ tap.js            [待写] adb tap + 等待 + 截图回读校验
├─ board.js          [待写] 手机牌面 → 与 PC board.json 同构的 JSON
└─ bot_mobile.js     [待写] 复用 apply_plan 的步序，把点击换成 adb tap
```

求解器**完全不用改**：`dfs_nopark.js` / `verify_plan3.js` 吃的就是
`board.json`（`{cells:[{id,color,rowNum,columnNum,layerNum}], handMax}`）。
只要 `board.js` 能产出同构 JSON，PC 侧全部资产直接复用。

## 5. 里程碑

| 阶段 | 内容 | 完成判据 |
|---|---|---|
| M0 | 通路 | `adb_probe.js` 抓到关卡截图；`input tap` 点中一张牌 |

| M4 | 执行 | 手机端跑完一关，结算页出现「挑战成功」 |
| M5 | 无人值守 | 手机端自跑（Termux + python）或 PC 常驻 adb 轮询 |

## 6. 风险

1. **视觉路线在密集关胜率不足**：现有视觉求解器没有前瞻，500+ 张的关卡
   在槽位接近上限时只能靠试探。若走 A，必须先补「暗卡类型信念分布 + 信息增益」。
2. **B 路线脆弱**：XWeb 版本一变就废，且手机上 frida 常驻容易被检测。
3. **点击延迟**：手机端 `input tap` 有 100~200ms 系统延迟，动画期间点击会丢，
   必须"点后截图确认"，这会显著拉长一局的耗时（879 张 × 2 次截图 ≈ 十几分钟）。
4. **合规风险**：与 PC 版一致，违反用户协议，风险自负。
